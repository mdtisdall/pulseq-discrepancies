# DIS-0070: The [SIGNATURE] hash of a file with CRLF line ends

## Summary

The specification says that the hash covers the file up to the new line
character that precedes `[SIGNATURE]`, and that this character is stripped
for the verification. For a file with CRLF line ends the C++ reader hashes
one byte less: it drops the whole empty line `\r\n` before `[SIGNATURE]`. So a
CRLF file signed by the rule of the specification fails the reader's check (a
warning), and one signed by the reader's rule does not follow the
specification. pypulseq 1.5.0.post1 on Windows writes such files with a hash
that matches neither rule. A hash that does not match the file is otherwise
not a discrepancy: no source requires a reader to reject it.

## What each source does

| Source | What it does |
|---|---|
| Specification | "The signature is generated by hashing the readily exported file … and appending the [SIGNATURE] section. The new line character preceding the keyword [SIGNATURE] is part of the signature and needs to be stripped away for the signature verification." (section 2.4, `spec:223`). It has no "must" to verify the hash. |
| C++ reader | `buildFileIndex` hashes each line with its line end, and holds back a line that is only `"\n"` or `"\r\n"`; it drops that line when the next line is `[SIGNATURE]` (`cpp:1771-1788`). It compares the stored hash, in lower case, with the computed one (`cpp:1631`, `cpp:1649`); a mismatch is a warning, "signature validation failed!" (`cpp:1650-1651`), and the file is read. |
| MATLAB Pulseq | `write` opens the file with `fopen(filename, 'w')`, which writes LF on every system, and hashes the bytes of the file (`write.m:17`, `write.m:267-272`). `read` stores the hash and does not check it (`read.m:85-93`). |
| pypulseq 1.5.0.post1 | `write` opens the file in text mode with no `newline` (`write_seq.py:52`), so on Windows each line ends with `\r\n`; it then reads the file back in text mode, where `\r\n` becomes `\n`, and hashes that text (`write_seq.py:258-261`), and appends the signature in text mode (`write_seq.py:264-277`). `read` stores the hash and does not check it (`read_seq.py:94-99`). |
| pypulseq master | `write` opens the file with `newline='\n'` and hashes its bytes (`write_seq.py:52`, `write_seq.py:258-261`): LF on every system, since pulseq/pypulseq#429 (commit `c977214`, 2026-10-12). `read` does not check the hash. |

## Impact

For an LF file the two rules hash the same bytes, so files of MATLAB Pulseq
and of pypulseq master are verified alike. A CRLF file signed by the rule of
the specification is reported as invalid by the scanner's reader; other
readers of signatures may follow the specification (mdtisdall/pypulseq-issues
draft 14 notes that KomaMRI.jl accepts the specification's hash and not the
reader's). Every file that pypulseq 1.5.0.post1 writes on Windows has a hash
that matches neither rule, so the reader warns on each of them; that is fixed
on master, not yet in a release.

## Suggested resolution

The specification: say which bytes are hashed when the line ends are CRLF.
The reader's rule decides on the scanner, so the specification could state
it: the hash covers the file up to the end of the last line before the empty
line that precedes `[SIGNATURE]`, and that empty line (`\n` or `\r\n`) is not
part of it. Or the C++ reader follows the specification and drops only the
`\n`.

## Report

Draft, to pulseq/pulseq (the text of mdtisdall/pypulseq-issues draft 14, branch
`docs/14-crlf-signature`, commit `14b320c`, in short):

> **Signature: for a file with CRLF line ends, the scanner's reader hashes
> other bytes than the specification says**
>
> Section 2.4 says that the new line character before `[SIGNATURE]` is
> stripped for the verification. `ExternalSequence::buildFileIndex`
> (`ExternalSequence.cpp:1771-1788`) drops the whole empty line before
> `[SIGNATURE]`, `\n` or `\r\n`. For an LF file the two agree; for a CRLF file
> they differ by the `\r` of the empty line. The attached file signed by the
> specification's rule fails `isSignatureCheckSucceeded`; the same file
> signed by the reader's rule passes. Could section 2.4 say which bytes are
> hashed for CRLF line ends (the reader's rule decides on the scanner)?
